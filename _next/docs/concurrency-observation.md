## A′.2 在途上限：**判据怎么设计才不自欺**【实测】

配置：`InFlightOptions.MaxPerAccount = 2`（`InFlightLease.cs:137`）。

**⚠ 这一步最容易自欺** —— 「每号最多 2 个」这个观察**本身证明不了上限生效**：

```
N 个请求 / M 个号时，**纯轮询**的预期最大值也是 ceil(N/M)：
    N=12, M=8 → ceil(1.5) = 2   ← 与「上限=2」**巧合一致**，测不出区别
```

**⇒ 必须选「两者会分岔」的场景：N > M × 上限。**

```
N=24, M=8, 上限=2 → 上限生效 ⇒ 单号同时最多 2
                     上限未生效 ⇒ 单号 3（24/8）
```

**还要区分「同时」与「先后」**：「单号 3 个请求」可能是**先后完成**的（串行复用），
那不算违反上限。所以用 `at - durationMs` **反推每个请求的时间区间**，再算**最大重叠**。

**原始输出：**

```
并发 24 / 号 8 → 码全 200: True
每号承担: {'7552f039:': 3, '1d754ce3:': 3, '1c9ad0bd:': 3, '346eb4c1:': 3,
           '3e563042:': 3, 'f9d03736:': 3, 'a23db308:': 3, '4f6e58b2:': 3}
★ 单号最大时间重叠 = 3 （上限=2 ⇒ 生效则应 ≤2）
⇒ 判定: **上限未生效**（观察到 3 个同时压同一号）
```

**加权细节（同一次运行，两个账号的重叠重建）**：

```
账号 a23db308:  区间 06:51:50.893→06:51:57.394 / 06:51:50.927→06:52:12.313 / 06:51:50.962→06:51:55.228
                三个起点相差 **< 70ms** ⇒ 确实是同时，不是先后
                ★ 最大重叠 = 3
账号 f9d03736:  区间 06:51:50.888→… / 06:51:50.922→… / 06:51:50.956→…
                ★ 最大重叠 = 3
```

⇒ **3 个请求真的同时在跑**（不是先后复用）。**上限 2 没有被执行。**

## A′.3 为什么「上限未生效」**不是 t66 修复的回归**【推断】

这条很重要，别记成"修复引入的新缺陷"：

```
① 上限靠 `Acquire` 维护 `InFlight`（`AccountPool.cs:188` 注释自述：
   「InFlight 由 Acquire 的租约维护；Pick 路径下恒为 0」）
② 实测 `grep "\.Acquire(" src/BuddyDeck.Gateway/` → **0 命中**
③ 网关实际走的是 `_affinity.Select(...)` → `PickAccountWithAnyUsableModel(...)`
   → 内部遍历 `_pool.Members` 自己排序（`GatewayApp.cs:926+`），**全程不碰 InFlight**
```

⇒ **`InFlight` 在活路径上恒为 0 ⇒ 上限无从生效。**
这是 **t66 根因③「Acquire 从未接线」的延续** —— t66 修的是**排序**（分散），
**没有修接线**。**两件事，别混。**

**⇒ 用户诉求「并发走」已达成；「单号不被挤爆」还没有。**
（t19 交付了 `InFlightLease`/`Acquire`/`MaxPerAccount`，但**没有接线到请求路径**。）

**⚠ 标注为【推断】的理由**：代码路径与实测一致（恒为 0 ⇒ 上限不生效），
但我**没有做**「接线后再测」的实验（那要改 `src/`，out-of-scope）。

## A′.4 本脚本新增的判别能力（供后人）

`tools/live_eval_pool.py` 新增 `⑤ 在途上限是否生效`（可用 `--skip-cap` 跳过，因为它
一次发 **号数×3** 个请求，是本脚本最耗配额的场景）。

它**不是**简单数「每号几个」，而是：
1. 选 **N > M × 上限** 的并发数（让「生效」与「未生效」分岔）
2. 用 `at - durationMs` **反推时间区间**，算**最大重叠**（区分「同时」与「先后」）

**⚠ 该判据的局限（写在脚本注释里）**：`durationMs` 是网关自报的整数毫秒，
反推区间是**近似**；且只覆盖**已完成**的请求 —— 在飞的看不到。
所以算出的重叠是**下界**，不是精确峰值。

## 1. 观测手段（判据从哪来）

`docs/concurrency-verification-howto.md` §0① 定的规矩：

> 要验证 A 对 B 做了什么，就去 **B 那边**取证，**不要在 A 内部找计数器**。

本报告用的三条外部证据：

| # | 来源 | 给出什么 | 为什么可信 |
|---|---|---|---|
| ① | `/metrics` → `recent[].accountTag` | **网关自己记账时写下的**「这次用了哪个号」 | 它是**旁路记录**，不是选号逻辑自述 |
| ② | `/admin/accounts` → `uid` / `label` | 把 `accountTag` 反查回**人能看懂的名字** | `accountTag` = `uid[..8] + ":"`（与 `GatewayApp.AccountTagOf` 对齐） |
| ③ | `/admin/pools` → `id` / `isDefault` | 池这一维 | 见 §4 的缺陷 |

**没有**使用 `AccountPool.SelectionCount` 之类的内部累计值 —— 它回答的是「历史上被选过几次」，
回答不了「此刻这个请求用了哪个号」。

## 3. ❌ 核心发现：并发与串行**都只用一个号**

### 3.1 实测输出（原始）

**6 个并发（19 个号可用）：**

```
② 并发分布（同时发 6 个请求）
  HTTP 状态码：[200, 200, 200, 200, 200, 200]
  墙钟耗时：22.3s（6 个并发）
  账号分布（来自 /metrics.recent 的 accountTag）：
     3e563042:      主号         6 次          ← ⚠ 6 个请求全在「主号」上
```

**连跑 3 轮 × 4 并发（复现性）：**

```
第1轮: 码=[200, 200, 200, 200] 用到号数=1 分布={'3e563042:': 4}
第2轮: 码=[200, 200, 200, 200] 用到号数=1 分布={'3e563042:': 5}
第3轮: 码=[200, 200, 200, 200] 用到号数=1 分布={'3e563042:': 5}
```

**3 轮完全一致 ⇒ 这是确定性行为，不是巧合。**

### 3.2 根因【推断 —— 读代码得出，未做单变量实验】

`src/BuddyDeck.Core/AccountPool.cs:177-181`：

```csharp
var picked = candidates
    .OrderBy(m => m.Entry.ExpiresAtMs == 0 ? long.MaxValue : m.Entry.ExpiresAtMs)  // ← 主键
    .ThenBy(m => m.SelectionCount)                                                 // ← 次键
    .First();

picked.SelectionCount++;   // 只在锁内递增，用来自证「我没在重复选」
```

**`ExpiresAtMs` 是主排序键，`SelectionCount` 只是平局时的次键。**

而 §2 实测的 19 个号**过期时间各不相同**，其中「主号」`3e563042` 的 `expiresAtMs`
**最小** ⇒ 它**永远是 `OrderBy` 的第一个** ⇒ `ThenBy(SelectionCount)` **永远轮不到生效**。

⚠ **标注为【推断】的理由**：我没有做「把主号改冷却，看负载是否转移」的单变量实验
（那需要走 `/admin/*` 或直接构造池状态，而真机没有「标记某号冷却」的端点）。
**代码路径与实测分布一致，但"一致"不等于"证明了因果"。**

### 3.3 这条为什么是用户诉求的反面

用户要的是「不出现一个号限额还得手动切换」。当前行为意味着：

> **在「主号」被限流之前，所有请求都压在主号上。**
> 一旦主号被限，`Pick` 才会选下一个 —— 也就是**用户感知到的「限额了才切」正是现状**，
> 而「并发走」这个前提**从未成立**。

**⇒ 「自动换号」是有的（t28 两层降级链），但「并发分散」没有。**
这两件事常被混为一谈，实测表明它们**不是同一个能力**。

## 4. ⚠ 异常项（原始输出，不做描述性转述）

### 4.1 `/admin/pools` 的 `accountCount` 恒为 0，与 `/admin/accounts` 自相矛盾

**原始输出（19 号网关，网关确实在用这些号）：**

```
GET /admin/pools →
[{"id": "default", "displayName": "默认池", "port": 8795, "apiKey": "",
  "running": true, "accountCount": 0,          ← ⚠ 0
  "isDefault": true, "lastError": null}]

GET /admin/accounts →
[{"id": "3e563042-…:", "label": "主号", "uid": "3e563042…", "active": false},
 … 共 19 条 …]

GET /metrics → recent[].accountTag = "3e563042:"   ← 证明在用「主号」
```

**同一进程，三个端点讲三个故事。** 而 `POST /v1/chat/completions` 返回 200
（即**确实在用**那些号）。

**根因【推断】**：`AdminEndpoints.cs:765-781` 的 `VaultPathOf` 在默认池上**忽略 `--vault` 的文件名**：

```csharp
var defaultHome = Path.GetDirectoryName(_options.ResolveVaultPath()) ?? …;
var home = PoolRegistry.ResolveVaultHome(poolsRoot, defaultHome, pool);
return Path.Combine(home, _variant.VaultFilename);   // ← 拼出 <vault目录>/auth.cn.json
```

实测推演：`--vault .local\vault-test.json` ⇒ 它去读 `.local\auth.cn.json`（**不存在**）
⇒ `Vault.Read` 返回 null ⇒ `Accounts.Count` → 0 ⇒ 而 `catch { return 0; }` 把它变成
**与「池里真的没有号」不可区分的 0**。

**⇒ 又一条「静默失败」**（与 t53 那条 UA 同源：失败被吞成正常值）。

已**报给 gateway**（含复现步骤与建议修法）。**影响面**：`accountCount`、
`POST /admin/pools` 返回的 `vaultPath`（`:692`）、`remove` 的 `vaultKeptAt`（`:734`）**同源**。

### 4.1b ✅ 修复已复验（我独立跑的，非转述）

**原始输出（修复后，同一个 19 号保险库）：**

```
GET /admin/accounts → 19 个号
GET /admin/pools    → [{"id": "default", "displayName": "默认池", "port": 8795,
                        "apiKey": "", "running": true,
                        "accountCount": 19,      ← 修复前是 0
                        "isDefault": true, "lastError": null}]
accountCount = 19  |  账号列表长度 = 19  → ✅ 一致
```

**修法**（gateway 实施，我复验）：默认池改用 `_options.ResolveVaultPath()` ——
**唯一的真源**（网关实际读号的那个路径），不再按「池目录约定」重推。

**附带改进**（采纳了我建议的方向）：
- 文件不存在 → 返 0，记 Debug（新池的正常状态，不吵）
- **读失败 → 返 `-1` 并记 Warning**（`-1` = 「不知道有几个」⇒ 界面该显示「读不到」而不是「0」）
- 加了两条**跨端点交叉断言**回归：单看 `/admin/pools` **永远看不出 0 是错的**
  （「池里没号」本身是个合理状态）—— **这正是它藏得久的原因**

**⚠ 这条的意义超出它本身**：它是本任务**唯一的实际缺陷产出**，形态与团队反复踩的那类一致 ——
**「读不到」与「本来就没有」长得一样**。观测面自己的静默失败，会让人把错误状态当成正常状态。

### 4.2 模型降级确实工作（这是**好消息**，附原始输出）

用不存在的模型名触发上游拒绝：

```
POST /v1/chat/completions  {"model":"no-such-model-xyz", …}
→ HTTP 200（15.0s）

/metrics.recent：
{"model": "no-such-model-xyz", "usedModel": "hy3", "status": 200,
 "accountTag": "3e563042:", "attempts": 1, "upstreamStatus": 200}
```

**`model=no-such-model-xyz` → `usedModel=hy3`** ⇒ **模型降级链生效**，
客户端拿到了 200 而不是 400。**这是 t28 内层换模型的真机证据。**

### 4.3 网关进程在观测期间**被外部停过一次**（原因已查明）

第二次运行前发现 `8795` 连接被拒、进程已不存在。

**原因已查明（非产品缺陷）**：`8795` 是**共享的一次性端口**，多人在上面起实例。
团队规矩是「8795 上任何实例随便停」——
我那次是被另一位成员为了解锁构建而停掉的（他随后告知了我）。

**⇒ 这不是产品缺陷，但它是一个真实的观测中断**，记在这里因为：
**「进程被外部停掉」和「跑完了」在外部看起来一模一样**
（同 `concurrency-verification-howto.md` 坑 4 的道理：「命令返回了」≠「成功了」）。

⇒ **重跑建议**：跑之前先确认 `8795` 上的实例是**你自己的**；观测期间留意连接被拒。

## 5. 未能测的维度（如实列出，不假装测了）

### 5.1 全部号冷却时的行为 —— **本脚本不测**

原因（逐个说明）：

- `/admin/*` **没有**「把一个号标记冷却」的端点 —— 无法从外部构造该状态
- 靠自己打满真实配额去触发 ⇒ **消耗用户真实额度且不可控**
- 该场景**已由离线 E2E 精确覆盖**：
  `PoolAndRetryE2ETests.网关层_所有号都在冷却时返回429错误对象_不崩不返回_undefined`
  + 流式版本（t13 修复后全绿）

⇒ **本真机脚本不重复它。** 这不是缺口，是**分层**：
**能精确构造状态的场景归离线测试，真机只验那些"只能真机验"的（真实账号、真实配额行为）。**

### 5.2 「峰值并发」—— 本脚本**拒绝报告**

t19 的观测里有「峰值并发 = N」这个数。**真机上算不出它**：
`/metrics.recent` 每条只给 `durationMs` 与 `at`（完成时刻），**没有开始时刻**，
所以**无法还原"某时刻有几个在途"**。

⇒ 脚本里写的是**分布**（「用到几个号、各承担几次」）—— 那是能证明的；
**「峰值并发」留给离线夹具**（那里假上游能精确撑开窗口并计数）。

### 5.3 多池（t58）—— 只验到「列表可读」，**未验到「请求真的走不同池」**

```
GET /admin/pools → 1 个池（default）
```

我这次只起了**一个**网关实例 ⇒ 只有一个池。
**「请求走不同池」需要起多个实例（每个池一个进程）** —— 那超出了本次范围
（且 8795 是共享的一次性端口，起多实例会互相抢）。
⇒ **【未测】**，见 §7 的后续建议。

## 7. 建议（给队长排期用，不是实现）

1. **`Pick` 的排序键**（§3.2）—— 这是**用户诉求不成立**的直接原因。
   若目标是「并发分散」，负载（在途数 / SelectionCount）应当是**主键**，
   而 `ExpiresAtMs` 是**次键**。⚠ 但改排序键会动到 ui 实测过的零重叠行为
   （`docs/concurrency-verification-howto.md` §2），**需要一并复核**。
2. **t19 的 `InFlightLease` 似乎没有接线** —— 【实测】`grep _pool.Acquire` 在
   `GatewayApp.cs` 里 **0 命中**。t19 交付了 `Acquire`，但网关仍走 `Pick`。
   **这与 §3 是同一件事的两面**：没有在途概念，就没有分散的依据。
3. **`accountCount` 缺陷**（§4.1）已报 gateway。
4. **多池路由**（§5.3）需要**多实例**才能验，建议单独立项并指定互不冲突的端口。
