# 界面动作 → 网关请求：可见性验证怎么做

> 这份文档回答一个问题：**「我在界面上点了这个按钮，请求到底有没有发到网关？」**
>
> 它存在的理由：这个项目**反复栽在同一类静默失败上** ——
> 界面看起来一切正常，但请求压根没发出去（或发错了地方）。
>
> ```
> t18  HttpGatewayClient 缺 Authorization 头  → /metrics 与 /admin/* 一律 401
> t47  相对路径 --vault 静默失效             → 聊天全部 401 not_signed_in
> t53  目录刷新必定失败且静默降级            → 用户永远看不到真机模型目录
> ```
>
> 三次都不是「代码写错了」，而是**「看起来对，实际没通」** ——
> 而这类问题**单测和截图都抓不到**。

---

## 1. 方法：假网关（三选一里选它）

契约允许「断点 / 日志 / 假上游」三选一。这里选**假上游（假网关）**：

| 手段 | 能回答「请求到了吗」 | 能进 CI | 能验失败路径 | 判读成本 |
|---|---|---|---|---|
| 断点 | ✅ | ❌ 要 GUI 调试器 | 勉强 | 高（要人盯着） |
| 真网关日志 | ✅ 只能看到**到达的** | ❌ 要真网关在跑 | ❌ | 中 |
| **假网关** | ✅ | ✅ | ✅ | 低（一条命令） |

**关键区别**：真网关日志只能告诉你「谁来了」，
**看不到「本该来但没来」的那一半** —— 而静默失败的典型形态恰恰是后者。

### 做法

起一个「把收到的每个请求都记下来」的假网关，让**真正的界面**指向它：

```
BUDDYDECK_PORT=<假网关端口>     ← 界面读它决定往哪发（App.xaml.cs:141）
BUDDYDECK_API_KEY=<任意值>      ← 界面读它决定带不带 Authorization（:152）
```

**这两个环境变量是界面本来就支持的**（`BUDDYDECK_OFFLINE` 是同一族），
所以**不需要改 `src/` 任何代码**。

### 为什么这是「真」验证

界面发的是**真 HTTP**（真 `HttpClient`、真序列化、真鉴权头组装），
假网关收的是**真请求**。被替换掉的只有「网关那台机器」——
而那正是要观察的对象。**所以「请求到达了吗」这个问题拿到的是真答案。**

## 2. 命令

```bash
cd D:\workfandaiapi\_next

# ① 默认：三类交互的请求 + 失败路径（不需要 GUI，随时可跑）
python tools/click_trace.py

# ② 机器可读（给别的脚本消费）
python tools/click_trace.py --json

# ③ 只跑某一类交互
python tools/click_trace.py --run 聊天

# ④ 起**真界面**，看它启动时到底发了什么（需 GUI 环境）
python tools/click_trace.py --with-app

# ⑤ 真界面 + 网关**确实没启动**（验「明确失败而非静默」，需 GUI）
python tools/click_trace.py --offline-app
```

退出码：`0` = 全绿；`1` = 有断言失败。

## 3. 判读方式

### 3.1 输出长什么样

```
§1 三类交互 → 请求到达假网关
  PASS  发起聊天 → POST /v1/chat/completions 到达网关
  PASS  发起聊天 的路径与方法正确
  PASS  发起聊天 带 Authorization
  PASS  发起聊天 的请求体是合法 JSON 且带 model/参数
  ...
§2 失败路径：网关未启动 / 拒绝连接
  PASS  网关未启动时，请求得到明确的连接失败（状态码 0 + 非空错误）
  PASS  网关拒绝请求时，客户端拿到失败而不是静默成功
  PASS  拒绝场景下请求仍留下了到达记录（区分「没发」与「被拒」）

ALL GREEN — 20 passed, 0 failed, 20 total
```

### 3.2 每个断言的**判据**

| 断言 | 判据 | 它挡住什么 |
|---|---|---|
| `… 到达网关` | 假网关的记录数在请求后 +1 | **请求压根没发出去**（t18/t47/t53 的形态） |
| `… 的路径与方法正确` | 收到的 method/path 与探针一致 | 打错端点（比如 `/admin/account` 漏了 s） |
| `… 带 Authorization` | 收到的头里有 `Authorization` | **鉴权头没带**（t18 —— 表现是「无端 401」） |
| `… 请求体是合法 JSON` | 体能被 `json.loads` 且非空对象 | 序列化坏了 / 发了空体 |
| `网关未启动时…明确连接失败` | 状态码 `0` 且错误文本非空 | **静默无反应**（最危险：用户以为在加载） |
| `拒绝场景下仍留下到达记录` | 记录数 ≥ 1 | 区分「**没发**」与「**发了被拒**」——两者排查方向完全不同 |

### 3.3 失败时怎么读

```
FAIL  切换池（启停） → POST /admin/pools/pool-1/state 到达网关 — 假网关没收到任何请求
```

**这一行就是结论**：界面那条路径没有发出请求。
接下来看 `ACTION_PROBES` 里这一条的 `why`（它写着对着 `IGatewayClient.cs` 哪一行抄的），
去那一行检查：是不是 `PostAsync` 的调用被短路了、参数拼错导致抛异常被吞了、等等。

反过来如果显示：
```
PASS  切换池（启停） → … 到达网关
FAIL  切换池（启停） 带 Authorization
```
那就是**发出去了但没带凭据** —— 正好是 t18 那个 bug 的形态。

### 3.4 `--with-app` / `--offline-app` 的输出

这两个模式要 GUI，**断言的是硬事实**（进程不崩、正常退出、截图产出），
**文案正确性交给人工看一眼**：

```
§4 真 App + 网关确实未启动（验明确失败而非静默）
  PASS  网关未启动时 App 仍能正常跑完（不崩、不挂死）
  PASS  离线状态下正常退出（退出码 0）
  PASS  离线截图已生成（6 张）
  需人工看一眼「总览」截图里的「连不上网关」卡片是否在：
      C:\Users\...\Temp\clicktrace-offline\ui-dashboard.png
```

> **为什么不把「文案对不对」做成自动断言**：那要靠 OCR / 像素比对，
> 那种断言的**假阳性率比它挡住的 bug 还多**（改个字号就红）。
> **如实标为「需人工看一眼」，比造一个看起来自动、实际不可靠的检查强。**

**已人工核验过一次**（2026-10-07）：离线截图里
标题栏显示「网关未启动：到「设置」确认端口」，
总览页有一张醒目的「**连不上网关** / 网关没有启动」卡片 —— 是明确失败，不是静默。

## 4. 三类交互的探针表

`tools/click_trace.py` 顶部的 `ACTION_PROBES` 就是这张表，
每条都对着 **`src/BuddyDeck.App/Services/IGatewayClient.cs` 的实现**抄：

| 界面动作 | 请求 | 对着哪行抄的 |
|---|---|---|
| 发起聊天 | `POST /v1/chat/completions` | `IGatewayClient.cs:459` |
| 刷新账号（列账号） | `GET /admin/accounts` | `:694` |
| 刷新账号（看指标） | `GET /metrics` | `:690` |
| 切换池（列池） | `GET /admin/pools` | `:720` |
| 切换池（启停） | `POST /admin/pools/{id}/state` | `:727` |

> ⚠ **界面改了实现，这张表要跟着改。** 所以它放在脚本顶部显眼处，
> 而不是散在各函数里 —— 改的时候一眼能找到。
>
> 反过来这也是它的一个**额外价值**：探针表与实现不一致时，
> 说明有人改了请求路径但没同步这里 —— 那本身值得看一眼。

## 5. 什么时候用它

| 场景 | 用哪个模式 |
|---|---|
| 新加了一个界面动作（按钮/页签） | `python tools/click_trace.py --run <动作名>` |
| 改了 `HttpGatewayClient` | 默认模式（全跑） |
| 「界面点了没反应」的排查 | 默认模式 → 看哪条 `到达网关` 是 FAIL |
| 怀疑鉴权头没带 | 默认模式 → 看 `带 Authorization` |
| 改了启动装配 / 端口 / key | `--with-app`（看真界面实际发了什么） |
| 「网关没启动时界面什么样」 | `--offline-app` + 人工看截图 |
| 想进 CI | 默认模式（无 GUI 依赖、无网络、无真实账号） |

## 6. 边界（它不做什么）

```
✅ 回答「请求有没有到达」「路径对不对」「鉴权头带没带」「体是不是合法 JSON」
✅ 验「网关不可用时的失败路径」
❌ **不验业务语义** —— 假网关的响应是「形状够用」而不是真实的；
   业务正确性归 Gateway.Tests / E2E.Tests（那两个跑真网关逻辑）
❌ **不点真实界面按钮** —— 界面动作要人点，本工具验的是「该动作对应的请求」
   （`--with-app` 能看到界面**启动时**自发发的请求，但点不了按钮）
❌ **不碰真实账号** —— 假网关从不连上游，跑一百次也不消耗配额
```

**最后一条尤其重要**：这个工具**永远不该**指向真实上游。
它的价值在于「可以随便跑」—— 一旦有副作用，就没人敢跑了。

## 7. 与其它工具的分工

```
tools/click_trace.py      界面 → 网关这一跳（本工具的战场）
界面的 --probe            界面能不能**渲染**（截图；证明不了请求发了）
界面的 --selftest         界面的调用契约（「永不抛」；不验到达）
FakeUpstreamHandler       网关 → 上游那一跳（`docs/test-support.md`）
```

**三跳各有各的工具，别互相替代**：
「界面渲染正常」+「网关与上游通信正常」**推不出**「界面到网关这一跳是通的」——
t18/t47/t53 三次都栽在中间那一跳没人验。
