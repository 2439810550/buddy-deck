## 0. 一句话结论

**两个对象取向不同，BuddyDeck 该学的次序也不同：**

| 项目 | 取向 | 页面数 | 单页厚度 |
|---|---|---|---|
| `workbuddy-switch` | **深** —— 5 页，每页做透 | 5 页 | 58–84 KB/页 |
| `workbuddy-manager` | **广** —— 20+ 路由铺开 | 20+ | 21–91 KB/页 |
| **BuddyDeck 现状** | **薄** —— 6 页，合计 94 KB | 6 页 | 7–30 KB/页 |

**BuddyDeck 六页合计 94,550 字节**，而 switch **单是账号卡片组件就 51,943 字节**。

结论：**先学 switch 的「深」** —— BuddyDeck 是桌面工具，用户核心诉求就是管账号、看积分。
页面数量不缺，**每个页面的信息密度和操作深度缺得厉害**。

## 2. 关键：switch 的账号卡到底装了什么

这是本次对标**最有价值的发现**。`account-card.tsx` 51,943 字节里做的事：

### 2.1 一张卡 = 一个账号 + **五个可切换目标**

实读 `account-card.tsx:587–702`，同一张卡上并排五个「设为当前账号」按钮：

| 目标 | 行号 | 状态机 |
|---|---|---|
| WorkBuddy | 587–602 | 已登录 / 可切换 |
| CodeBuddy IDE | 615–624 | **区分「未检测到 IDE」** |
| VS Code 插件 | 637–648 | **区分「未装 VS Code / 未装扩展 / 可切换」三态**（`:189–193`） |
| JetBrains 插件 | 665–676 | **区分「未装 IDE / 未装插件 / 可切换」**（`:196–200`） |
| CodeBuddy CLI | 693–702 | **区分「未接入」** |

**为什么这很关键**：BuddyDeck 现在的「切号」只有一个动作（切网关用的号）。
而真实用户的诉求是**「把这个号推到某个工具里去」** —— 每个目标各有自己的安装态、
自己的"当前是谁"、自己的并发锁（`:284–316` 有 4 个 busy 标志）。

### 2.2 积分不是一个数，是**多个资源包**

实读 `:66–76` 与 `:366–394`、`:738–772`：

```ts
function creditResources(credit?: CreditExpiry): CreditResource[] {
  return (credit?.resources ?? [])
    .filter((resource) => resource.remaining > 0)      // 用完的不显示
    .sort((l, r) => (l.resource.expireAt ?? ∞) - (r.resource.expireAt ?? ∞));  // 按到期升序
}
```

界面呈现（`:738–772`）：
- 标题行：`N 个积分包` + 右侧 `X 积分将在 7 天内到期` / `最近到期 MM/DD HH:mm` / `当前积分长期有效`
- 列表**固定两个槽位**，多出来的收进「查看全部积分包」弹框（`:753`）
- **空态也占一个槽位**（`:763–765`「暂无可用积分」）—— 注释说明了理由：避免与空态文案重复
- 每条：`名称` + `剩余积分` + 到期时刻（精确到分，`formatCreditExpiry` `:31–38`）

**对比 BuddyDeck**：我们的 `AccountSummary` 只有一个 `ExpiresAtMs`（token 有效期）。
**「还剩多少积分、哪笔先过期」完全没有** —— 而这恰恰是用户每天最关心的数字。

### 2.3 状态用**图标 chip**，不占文案宽度

实读 `:80–124` 的 `statusIconChip()`，注释写明了设计意图：

```ts
/**
 * 纯图标状态 chip：状态由图标 + 色调 + tooltip 共同表达，不再占文案宽度。
 * 签到、旅行与模型限额共用这一份实现（角标样式、`aria-label`、tooltip 位置统一）。
 */
```

三个具体机制：
- **数量角标**：`count > 1` 才显示（`:96`「单个受限模型不需要角标」）
- **置灰表示"未激活但正常"**：`:98`「未旅行是多数账号的常态：只留置灰图标，文案交给 tooltip」
- **模型限额 chip**（`:227–248`）：悬停按**恢复时间升序**列出全部受限模型
  —— 注释 `:230` 解释了为什么升序：「最早的解锁时刻最有行动价值」

### 2.4 自动签到是**每账号可关**的

实读 `:448–462`：`自动签到已关闭` 状态独立于全局开关（`:270` 注释「独立于全局开关」）。

## 5. 界面结构改造方案（具体到可执行）

### 5.1 导航：**保持 6 页，不加页** —— 但每页加深

**理由（这是本次最重要的结构判断）**：

- manager 用 20+ 路由，是因为它是 **Web 端 / 多人协作**，需要 URL 可分享、可深链
- switch 用 5 页，是因为它是 **桌面工具**；它把复杂度放进了**页面内部**
- **BuddyDeck 是桌面工具**，且已有明确的「仪表盘→列表→详情」信息架构（HANDOVER 第五节）
- **加页面会增加导航负担，而不增加能力** —— 用户找不到的东西等于没有

**所以：不新增一级导航。改为在两处加"二级层"。**

### 5.2 三个具体改动

#### 改动 A：账号页加「详情抽屉」（学 switch 的对话框）

现在账号页是**左列表 + 右详情**。保持这个结构，但**右侧详情要加深**：

```
右侧详情（现在只有 6 个字段 + 4 个动作）
  ↓ 扩展为分区：
┌─ 基本信息 ─────────── 标签 / uid / 类型 / 域名 / 备注
├─ 积分 ────────────── ★ 新增
│   总余额 N
│   ├ 资源包 A   1,200 积分   12/31 23:59 到期
│   ├ 资源包 B     340 积分   11/15 08:00 到期
│   └ 查看全部积分包 →
├─ Token ──────────── 有效期 / 剩余 / 签发时间 / 最后续期
├─ 状态 ───────────── 在线/冷却/降权/一直失败 + 原因
│                     模型限流：glm-5.2（3 分钟后恢复）★ 新增
└─ 动作 ───────────── 签到（★新增）/ 切到网关 / 续期 / 改名 / 删除
```

**分区来源**：switch `account-card.tsx` 的卡片就是按这个顺序组织的
（积分段 `:738`、状态 chip 段 `:448`、动作段 `:539–570`、切换段 `:587–702`）。

#### 改动 B：账号列表行加「积分 + 状态 chip」

现在一行是：`状态条 | 标签 · 类型 · uid · 域名 | 状态徽章 · 剩余时间`

改为：`状态条 | 标签 · 类型 · uid | 积分 N（最近到期 MM/DD） | 状态 chip 组`

**chip 组**（学 switch `:80–124` 的 `statusIconChip`）：
- 纯图标 + tooltip，**不占文案宽度**
- 数量角标只在 `>1` 时显示
- 「未激活但正常」用**置灰**表达（如「未签到」）

#### 改动 C：仪表盘加一行「今日概览 + 积分风险」

现在仪表盘已有：网关块 / 账号块 / 指标块 / 最近请求。

**新增两行**（放在账号块之后）：
```
今日：  12 次请求 · 3 次失败 · 45,231 Token
积分：  3 个账号 7 天内到期（共 2,100 积分）  → 去处理
```

来源：manager `dashboard:507–520`（今日 Token/请求/失败）、
switch `account-card.tsx:746`（近期到期）。

**为什么放仪表盘**：「积分要过期了」这件事必须**不点进去就能看到** ——

## 6. 与 BuddyDeck 现有设计的冲突点（需要先决策）

对标出一处**真实的设计冲突**，不能直接抄：

**switch 的卡片是"每个目标一个按钮"（5 个按钮并排）。**
BuddyDeck 的设计计划（`docs/ui-design-plan.md` §1.8 原则 2）明确规定
**「一个签名元素，其余安静」**，且 §2 特征 4 明确要避开
**「内容剁成卡片 + 一刀切圆角」**。

**冲突**：如果照抄 5 个按钮并排 + 卡片容器，会直接违反 design 已确立的反模板化原则。

**我的建议**（留给实现时定）：
- **信息照抄，形态不照抄**：积分分区、状态 chip、模型限流倒计时**全部要**；
  但容器继续用现有的**行 + 状态条 + 1px 分隔线**（不用卡片、不加阴影）
- 五个切换目标收进一个**下拉菜单**（保持"安静"），而不是并排五个按钮
- 这条需要 design 确认 —— **它的设计计划是视觉层的唯一真源**

## 13. 四条硬需求的界面落点 `[方案]`

### ① 多号池并行启用 → **接入池页改造**

**现状（队长核实）**：`AdminEndpoints.cs:464` `GET /admin/pools` 回**长度为 1 的数组（就是本实例）**；
`POST /admin/pools`（新增）→ **501**。⇒ **现在是硬限制**。

**界面落点**：**接入池页**（Page 3），从「单池展示」变成「多池管理」：

| 要素 | 做法 |
|---|---|
| 池列表 | 每池一行：**状态条 + 名称 + 端口 + 启停 + 账号数 + 今日用量** |
| 启停 | 行内 `ToggleSwitch`（**学 switch 的「支持工具」范式**，§10.6） |
| 账号归属 | 行内展开/详情显示「这个池用了哪几个号」 |
| 新建/编辑 | 侧栏表单：名称 / 端口 / API key / **账号集（多选）** |
| 池健康 | 每池：运行中/已停止/启动失败 + **该池的 attemptCount 比值** |

**参考位置**：manager 的 `upstreams` 页（`zh-CN.json` 的 `upstreams.*`）
就是「多上游（账号池分组）」—— **概念完全对应**，
它有 `probe 探测` / `boundKeys N 把密钥在用` / `defaultTag 默认` 三态。
**建议照它的信息结构，用我们的行式视觉。**

### ② 请求级可见（池 → 号）→ **请求日志页 + 总览页**

**现状**：`/metrics` 只有账号维度，**没有「池」这一层**；`RequestLog` 也没记 `poolId`。

**界面落点**：
- **请求日志页**：加**「池」列**（见 §12.2 ⑧ 的版式），与「账号」列并排
- **总览页**：最近请求那一行同样加池列
- **表达形式**：**两列并排**（池 / 账号），不合并成一个"默认池·主号"字符串 ——
  **分开才能排序和筛选**

**参考位置**：manager `logs` 页的 `rowKey / rowModel / rowMappedModel / colAccount`
就是这个思路（把"经过哪些环节"拆成多列，而不是拼一行）。

### ③ 自动并发分流 → **总览页展示 + 接人池页配置**

**现状**：核心已有（t19 在途计数 + t28 两层降级），但**多池之间没有分流**，用户要"不用手动切"。

**界面落点**：
- **总览页**：显示**分流实况** —— 「当前 3 个池在服务，本轮 12 个请求分到 4 个号」
- **接入池页**：每池一个**在途上限**配置（默认 2，与 t19 一致）
- **不要**做成设置项藏起来 —— 它是用户**要看见**的行为（"系统在帮我分流"）

**⚠ 依赖**：需要后端补 `poolId` 维度。**我出界面，后端由队长另派。**

### ④ 聊天框展示生图/生视频 → **聊天测试页改造**

**现状（队长核实）**：`ChatPage.xaml` 现在是**纯文本 `ItemsControl`**，
**完全没有 `Image`/`Media` 元素**，ViewModel 也没处理媒体。

**界面落点**：**聊天测试页**的消息列表，从「纯文本」改成「**内容块流**」：

| 元素 | 做法 |
|---|---|
| 图片 | `Image` + `MaxWidth`（不撑破气泡）+ **点击放大**（`ContentDialog` 或 `Flyout`）|
| 视频 | `MediaElement` + 原生播放条（**不做自定义播放器** —— 那是另一个项目的工作量）|
| 加载态 | 占位框 + `ProgressRing`（**尺寸固定**，避免图出来后布局跳）|
| 尺寸 | 图最多占气泡宽度；**长图限制最大高度**，超出可滚动 |
| 失败 | 说清"是上游没返回图"还是"下载失败"，给重试 |

**⚠ 需要注意的**：视频/图片来自网络 → **同样要过 §t52 的 URL scheme 白名单**思路，
且要限制下载大小（否则一个超大图能把界面卡死）。

**参考位置**：`manager` 的 `playground` 页**只有文本**（`zh-CN.json` 的 `playground.*` 无媒体字段）
—— **两个参考项目都没有这个能力**，所以**这条要我们自己设计**，没有现成可抄。**`[推断]`**
